# Database schema

Target model for the three PostgreSQL databases. `messaging-service` has no database.

Each service applies this SQL with Flyway on startup. The scripts are `user-service/src/main/resources/db/migration/V1__create_accounts.sql`, `plaza-service/src/main/resources/db/migration/V1__create_plaza.sql`, and `traceability-service/src/main/resources/db/migration/V1__create_order_status_change.sql`.

There is one PostgreSQL server and three databases. Tables live in `public`. A restaurant id stored in `user_db`, or a user id stored in `plaza_db`, is a logical reference. PostgreSQL cannot enforce a foreign key across databases.

Passwords and the delivery PIN are stored as bcrypt hashes. The stories call this encryption. bcrypt is one-way: the value cannot be read back.

## user_db

Accounts and roles. Login is email and password for every role.

```sql
CREATE TABLE role (
    id SMALLINT PRIMARY KEY,
    name VARCHAR(32) NOT NULL UNIQUE
);

INSERT INTO role (id, name) VALUES
    (1, 'ADMINISTRATOR'),
    (2, 'OWNER'),
    (3, 'EMPLOYEE'),
    (4, 'CUSTOMER');

CREATE TABLE app_user (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    first_name TEXT NOT NULL,
    last_name TEXT NOT NULL,
    identity_document TEXT NOT NULL UNIQUE,
    phone VARCHAR(13) NOT NULL,
    birth_date DATE,
    email TEXT NOT NULL UNIQUE,
    password_hash VARCHAR(72) NOT NULL,
    role_id SMALLINT NOT NULL REFERENCES role (id),
    restaurant_id BIGINT,
    CONSTRAINT identity_document_is_numeric CHECK (identity_document ~ '^[0-9]+$'),
    CONSTRAINT phone_shape CHECK (phone ~ '^\+?[0-9]+$' AND char_length(phone) <= 13)
);

-- birth_date is required only for an owner, and the person must be an adult.
-- That depends on the current date, so the application checks it.
-- restaurant_id is required only for an employee. It is the plaza restaurant
-- of the owner who created the account. The other roles leave it null.
```

`password_hash` is the bcrypt hash of the password. The password itself is not stored.

The first administrator is inserted by `user-service` before login is required. The row uses the same columns. Its hash is generated with bcrypt at that moment.

| Column | Story |
| --- | --- |
| `first_name`, `last_name`, `identity_document`, `phone`, `email`, `password_hash` | HU 1, HU 6, HU 8 |
| `birth_date` | HU 1. Owners only. |
| `role_id` | HU 1 forces `OWNER`. HU 6 forces `EMPLOYEE`. HU 8 forces `CUSTOMER`. HU 6 and HU 8 receive `idRol`. |
| `restaurant_id` | HU 6. The employee belongs to the calling owner's restaurant. |

## plaza_db

Restaurants, dishes, and orders.

```sql
CREATE TABLE restaurant (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name TEXT NOT NULL,
    nit TEXT NOT NULL UNIQUE,
    address TEXT NOT NULL,
    phone VARCHAR(13) NOT NULL,
    logo_url TEXT NOT NULL,
    owner_id BIGINT NOT NULL,
    CONSTRAINT restaurant_name_not_only_digits CHECK (name !~ '^[0-9]+$'),
    CONSTRAINT nit_is_numeric CHECK (nit ~ '^[0-9]+$'),
    CONSTRAINT restaurant_phone_shape CHECK (phone ~ '^\+?[0-9]+$' AND char_length(phone) <= 13)
);

CREATE INDEX restaurant_name_idx ON restaurant (name);

CREATE TABLE dish (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    restaurant_id BIGINT NOT NULL REFERENCES restaurant (id),
    name TEXT NOT NULL,
    price INTEGER NOT NULL,
    description TEXT NOT NULL,
    image_url TEXT NOT NULL,
    category TEXT NOT NULL,
    active BOOLEAN NOT NULL DEFAULT TRUE,
    CONSTRAINT price_is_positive CHECK (price > 0)
);

CREATE INDEX dish_restaurant_category_idx ON dish (restaurant_id, category);

CREATE TABLE customer_order (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    restaurant_id BIGINT NOT NULL REFERENCES restaurant (id),
    status VARCHAR(20) NOT NULL DEFAULT 'PENDING',
    assigned_employee_id BIGINT,
    pin_hash VARCHAR(72),
    CONSTRAINT order_status_known CHECK (
        status IN ('PENDING', 'IN_PREPARATION', 'READY', 'DELIVERED', 'CANCELLED')
    )
);

CREATE INDEX customer_order_restaurant_status_idx
    ON customer_order (restaurant_id, status);

CREATE UNIQUE INDEX customer_order_one_active_idx
    ON customer_order (customer_id)
    WHERE status IN ('PENDING', 'IN_PREPARATION', 'READY');

CREATE TABLE order_line (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_id BIGINT NOT NULL REFERENCES customer_order (id),
    dish_id BIGINT NOT NULL REFERENCES dish (id),
    quantity INTEGER NOT NULL,
    CONSTRAINT quantity_is_positive CHECK (quantity > 0),
    CONSTRAINT one_line_per_dish UNIQUE (order_id, dish_id)
);
```

`owner_id`, `customer_id`, and `assigned_employee_id` point at `app_user.id` in `user_db`.

`pin_hash` is the bcrypt hash of the PIN sent by SMS when the order becomes `READY`. It stays null before that. The SMS carries the PIN. The table does not.

Every line of an order must belong to `customer_order.restaurant_id`. PostgreSQL cannot express that with a foreign key, because `dish.restaurant_id` and `customer_order.restaurant_id` are two paths. The application rejects a line from another restaurant.

An order has no price column. Payment is out of scope.

| Column | Story |
| --- | --- |
| Restaurant `name`, `nit`, `address`, `phone`, `logo_url`, `owner_id` | HU 2 |
| Dish `name`, `price`, `description`, `image_url`, `category`, `restaurant_id` | HU 3 |
| Dish `active` default `TRUE` | HU 3. HU 7 flips it. HU 4 changes only `price` and `description`. |
| Order `restaurant_id`, lines, `quantity`, `status` default `PENDING` | HU 11 |
| `assigned_employee_id` | HU 13 |
| `pin_hash` | HU 14 generates the PIN. HU 15 checks it. |
| `status` | HU 11 `PENDING`, HU 13 `IN_PREPARATION`, HU 14 `READY`, HU 15 `DELIVERED`, HU 16 `CANCELLED` |

The partial unique index is the rule that a customer has at most one order in `PENDING`, `IN_PREPARATION`, or `READY`.

HU 9 lists restaurants by `name` and returns `name` and `logo_url`. HU 10 lists dishes of a restaurant and can filter by `category`. HU 12 lists orders of the employee's restaurant by `status`.

## traceability_db

One row each time an order changes status. Durations are computed from these rows. They are not copied onto `customer_order`.

```sql
CREATE TABLE order_status_change (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_id BIGINT NOT NULL,
    customer_id BIGINT NOT NULL,
    restaurant_id BIGINT NOT NULL,
    employee_id BIGINT,
    previous_status VARCHAR(20),
    new_status VARCHAR(20) NOT NULL,
    occurred_at TIMESTAMPTZ NOT NULL,
    CONSTRAINT trace_status_known CHECK (
        new_status IN ('PENDING', 'IN_PREPARATION', 'READY', 'DELIVERED', 'CANCELLED')
    ),
    CONSTRAINT trace_previous_status_known CHECK (
        previous_status IS NULL
        OR previous_status IN ('PENDING', 'IN_PREPARATION', 'READY', 'DELIVERED', 'CANCELLED')
    ),
    CONSTRAINT one_row_per_status UNIQUE (order_id, new_status)
);

CREATE INDEX order_status_change_customer_idx
    ON order_status_change (customer_id, order_id, occurred_at);

CREATE INDEX order_status_change_employee_idx
    ON order_status_change (employee_id, occurred_at)
    WHERE employee_id IS NOT NULL;
```

`order_id` points at `customer_order.id`. `customer_id` and `employee_id` point at `app_user.id`. `restaurant_id` points at `restaurant.id`.

The first row of an order has `new_status = 'PENDING'` and `previous_status` null. Time spent in a status is the gap between that row's `occurred_at` and the next one.

For HU 18, an order starts when `new_status` becomes `IN_PREPARATION` and finishes when it becomes `DELIVERED`. That interval belongs to `employee_id`. A `CANCELLED` order has no finish and is left out of the average. The owner filter is `restaurant_id`.
